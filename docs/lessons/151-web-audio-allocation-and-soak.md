# 第151課：六個播放器，不代表只建立六份瀏覽器音訊

這次先量測遊戲本身：30分鐘加速模擬暖機後約46.5 MB、1733個物件，沒有持續成長。但手機分頁還包含瀏覽器音訊、WASM和GPU，Godot物件數穩定不能直接排除重整風險。

`CampaignAudio` 已經重用六個 `AudioStreamPlayer`。問題是 Web 預設 Sample 播放：同一播放器重播時，底下仍會建立新的瀏覽器音源、聲道節點和音訊緩衝。實際音效架在120秒內約7185次請求、3813次接受播放，建立3835個音源，累計配置約542 MiB PCM；累計配置不是同時占用，更不是已證實的記憶體洩漏。

這次在 `project.godot` 設 `audio/general/default_playback_type.web=0`。這個 ProjectSettings 值的0代表Stream，和AudioServer的播放列舉不是同一組數字。只加 `.web` 覆寫，原生設定不動。音樂原本已串流，現在讓腳步、戰鬥、環境及介面音效也走固定混音輸出；六路池和原本音量、冷卻照常工作。

相同120秒串流對照約7184次請求、3926次接受播放，瀏覽器Sample音源／緩衝配置為零。這表示避開了反覆配置路徑；不代表整個遊戲記憶體為零，也不能代替iPhone的30–60分鐘實機驗收。串流在Web可能有較高延遲，仍需確認命中、腳步和介面聲音的實際手感。

重現工具是 `tools/build_web_soak.py`：`--scene audio`比較同一音效架兩種後端；`--scene campaign`匯出隔離存檔的32分鐘實景測試。測試工具只在明確指定時成為入口，正式遊戲保持原主選單。觀察實際配置、畫面幀率、音量峰值、存讀成功及集合大小，比只檢查一個設定值有效。

發布前使用修正為只停止一次的診斷工具再測：Sample在120秒接受3760次音效、累計3802份緩衝；Stream接受3779次、零Sample緩衝，停止5秒後兩者物件皆回1696。完整場景另外跑滿32分鐘並六次存讀成功。原始資料與限制見[本版驗收](../reports/release-0.0.74/preflight.json)。
