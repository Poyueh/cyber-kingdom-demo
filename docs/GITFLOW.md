# Gitflow

`main` 保存正式發行版本；日常可遊玩的整合成果放在 `develop`。每個開發單元從 develop 建立 feature 分支，先測試再實作，完成後以 merge commit 保留工作單元。

```text
main ────────────────────── 正式發行
  └─ develop ────────────── 下一版本整合
       └─ feature/<name> ── 開發與驗證 ── merge --no-ff → develop
```

## 每日開發

1. 檢查工作目錄，不覆蓋未提交修改。
2. 從 develop 建立 `feature/<name>`。
3. 為新規則寫測試，確認合理失敗，再完成實作。
4. 同步三語遊戲說明、操作提示、進度與教學，重建指南；執行 `bash tools/check.sh` 並完成對應試玩。
5. 提交功能和文件，以 `--no-ff` 合併回 develop。
6. 每次新功能預設接續release流程，只發布H5森林Demo及對應規格／指南，驗證套件與線上內容一致。完整主遊戲同步程式並供本機Godot執行；其餘平台只有當次指定才匯出和發布。除非使用者當次要求只留本機，不停在H5尚未發布狀態。

例如下一個營地測試可用 `feature/camp-economy-prototype`。`test:`、`feat:`、`fix:`、`docs:` 描述提交目的。

## 發行與修補

- 準備可發行版：由 develop 開 `release/<version>`，只處理發行與驗證問題。
- 驗證完成後回合 main 和 develop，於 main 建正式版本 tag。
- 已發行版的緊急修補：從 main 開 `hotfix/<name>`，修好也回合 main 與 develop。
- 尚未簽署、未通過裝置驗證的訓練場不當作正式上架版本。

本地 Git 提交與 GitHub 備份是不同步驟。提交完成不代表已推送；不使用 force push，不重寫歷史，不提交憑證。使用者已持續授權新功能同步說明與試玩發佈；遠端目的地為 Poyueh/cyber-kingdom-demo。

## 聊天發佈指令

2026-10-21使用者指定新的預設：新功能完成後只公開H5森林Demo；共同玩法仍更新主遊戲與Demo，主遊戲預設在本機Godot執行。下列為在開發聊天中傳送給代理的自然語言指令，不是終端機命令。

| 指令 | 執行範圍 |
| --- | --- |
| `發佈 H5 Demo` | 更新森林試玩站、對應規格與指南；這也是未指定平台時的預設。 |
| `發佈 H5 主遊戲` | 匯出並更新完整七星主遊戲Web入口。 |
| `發佈 Windows 主遊戲` | 建置並發布Windows主遊戲下載包。 |
| `發佈 macOS 主遊戲` | 建置並發布macOS主遊戲下載包。 |
| `發佈 Android 主遊戲` | 建置並發布Android debug APK。 |
| `發佈 iOS 主遊戲` | 匯出並發布待簽署的Xcode專案；不代表可直接安裝或App Store上架。 |
| `發佈 Windows、macOS Demo` | 僅處理列出的平台與森林Demo。其他平台同樣可將「主遊戲」換成「Demo」。 |
| `發佈全部平台，主遊戲與 Demo` | 明確要求恢復本次雙版本五平台打包發布。 |
| `只實作，先不要發佈` | 僅完成本機程式與文件更新，本次不公開新版本。 |
| `本機啟動主遊戲`／`本機啟動 Demo` | 啟動指定版別供操作試玩，不發布。Demo需使用隔離版別和存檔，不能只隱藏其餘六星選單。 |

未指定版別的額外平台指令，例如「發佈Windows」，預設為主遊戲。可明確附上版本；省略版本時使用目前已驗證、待發行的成果。打包前仍須完成該平台的必要驗證、分包與校驗；未實際上傳不能稱為已發布。正式商店上架、購買服務、付費帳號與簽署憑證另行處理。

H5-only發行最少保留Demo Web封包與SHA256SUMS.txt；不為湊齊附件而匯出其他平台。現有Pages已可接受缺少Main Web的Release，但部署會替換整站；下一次Demo-only發布必須保留先前/main/資產並核對實際版本，避免順帶移除既有入口。舊Release與附件維持原樣。

本機主遊戲：在Godot開啟此倉庫的project.godot，按F5從主選單開始；本地distribution.json預設full。直接執行來源專案不需要先匯出安裝包。
